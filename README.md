# Obsidrel Showcase

Official public showcase content for [Obsidrel](https://obsidrel.com/). The Core plugin and this showcase are distributed separately.

This repository contains **converted Obsidrel definitions and Minecraft resource-pack assets only**. It is not a catalog, an importer, or an addon. The showcase can be changed independently of the Core's release cycle.

> **Status:** Repository structure only. No showcase content has been published yet. The Core does not yet download these releases; that integration will be implemented separately.

## Showcase ZIP layout

The published `showcase.zip` will use this exact root layout:

```text
showcase.zip
├── resources/
│   ├── items/
│   ├── blocks/
│   ├── furniture/
│   ├── entities/
│   ├── armor-sets/
│   ├── cosmetics/
│   ├── actions/
│   ├── conditions/
│   ├── cooldowns/
│   ├── triggers/
│   ├── loot/
│   ├── recipes/
│   ├── fonts/
│   ├── sounds/
│   ├── variables/
│   └── ui/
│       ├── menus/
│       ├── huds/
│       └── components/
└── pack/
    └── assets/
        └── <minecraft-namespace>/
            ├── models/
            ├── textures/
            └── ...
```

Only the folders needed by the content have to exist. `resources/` contains YAML definitions and `pack/` contains the *contents* of a resource-pack source, including PNG, JSON, `sounds.json`, etc. Preserve the paths and namespace references already generated by the importers.

### Adding imported content

1. On a development Minecraft server, import from an official Obsidrel importer and test the resulting resources and pack.
2. Copy the **converted** `plugins/Obsidrel/resources/<category>/sourceimport_*.yml` files into the corresponding `resources/<category>/` folder here.
3. Copy the **contents** of each `plugins/Obsidrel/pack/sources/sourceimport-*/` into `pack/` here. Do not nest the `sourceimport-*` directory inside `pack/`.
4. Resolve conflicts when packages share the same namespace/path or resource key; ensure all references still point to existing files.
5. Credit the original creators in [ATTRIBUTION.md](ATTRIBUTION.md) and verify that redistribution is authorized.

Do not copy `SourceImporter/cache`, `SourceImporter/reports`, `pack/generated`, server configuration, logs, or storage data.

The Core's future showcase installer will discover definitions automatically and build the visual menu from the installed showcase content. No Java-side hardcoded list is intended.

## Publishing a version

After committing **real, authorized content**, create and push a version tag, for example:

```bash
git tag v1.0.0
git push origin v1.0.0
```

The GitHub Actions workflow validates the layout and publishes two **GitHub Release assets**:

- `showcase.zip` — package consumed by the Core
- `showcase.sha256` — SHA-256 checksum of the ZIP

A release with no resource YAMLs is rejected. Publishing a new release does not imply automatic updates of installed servers. The Core's future downloader should install only on first setup or after an explicit update action.

**Do not tag/publish until assets have been tested and creators have approved public redistribution.**
